Measured with PR-demo/t4_profile/session_cpu_split.sh during a live
textflood + batched-arm run on the T4, 2026-07-31. Two /proc/<pid>/stat
reads 45 s apart — no sampling profiler, because on 4 vCPUs a `top -b -d 2`
sampler was measured to move the send interval by 50 %.

session_cpu_split: window 45s, 4 vCPUs, payload=textflood
  Xorg (capture + X)    13.01 s =  28.9 % of a core
  payload               35.90 s =  79.7 % of a core
  xrdp encoder side     10.97 s =  24.4 % of a core
  ------------------------------------------------
  measured total        59.88 s = 132.9 % of a core = 1.33 of 4 cores

  -> neither Xorg (28.9%) nor the payload (79.7%) is pinned:
     the limit is elsewhere (encode service, flow control, or
     a serialisation between them). Do NOT attribute to CPU.

For comparison, the SAME box under the old xterm codeflood payload
(captures/e52_t4_batched_20260730/): the session Xorg sat at 92 % of a
core and was the ceiling. textflood moved it to 28.9 %.
